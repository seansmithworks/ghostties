# Variant F — Reveal on approach

**Thesis:** the card at rest carries zero chrome at all — no strip, no buttons, nothing but terminal. The liquid-glass sidebar-toggle and globe buttons only fade in when the pointer approaches the card's top edge, borrowing the reveal gesture from Arc/Dia's own hover-to-show chrome rather than committing to always-on controls like Variant D.

**Under the hard case:** the reveal is pointer-proximity-driven, not sidebar-state-driven — both mockup columns show the sidebar in the same open state, because the axis being demonstrated is "is the pointer near the top edge," not "is the sidebar open." That holds regardless of sidebar width: the buttons are still inset from the card's own top corners (16pt, matching D), so opening or closing the sidebar just moves the card's bounding box and the buttons ride along with it, same as D. The harder case is a trackpad or Magic Mouse user who never rests the pointer near the top of the card during a normal work session — reaching for the sidebar toggle then requires a deliberate mouse trip to a spot with no visible affordance until the pointer already arrives there.

**Biggest risk:** discoverability. A brand-new user has no visual cue that anything lives at the top of the card — the at-rest state is indistinguishable from "this app has no chrome controls at all." Arc and Dia get away with this because their reveal zone is the browser's own persistent top chrome, which users already scan; Ghostties has no equivalent anchor telling a first-time user to hover there. Without a first-run hint or a one-time animation, this variant risks looking feature-complete while hiding its only two controls behind a gesture nobody knows to try.
