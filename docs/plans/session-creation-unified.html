One way to start a session

Unifying seven creation entry points onto one composer

Project: Ghostties 2026-08-18 Draft — 2 design forks open

The verdict

Every session in Ghostties is already created by one function. SessionCoordinator.createQuickSession(for:template:…) (SessionCoordinator.swift:306) has six call sites and no rivals. There is no second spawn path, no duplicated wiring, no divergent side effects. This is a UI consolidation, not a refactor — the model underneath is already unified and the five front-ends are five different ways of picking two arguments.

So the work is: build one composer, parameterize it by entry point, and delete four bespoke pickers. What varies across entry points is only three things — everything else is constant:

  • Presentation — anchored popover (came from a row) or centered overlay (came from a keystroke or the toolbar).
  • Project state — locked (row knows it), pre-filled (cascade guessed it), or open (user picks).
  • Focus target — which field owns first responder on open.

Constant everywhere: the template list, the search behavior, the add-project chip, Return-to-commit, Esc-to-cancel, and the single call to createQuickSession.

Correction to the brief: there are seven distinct paths, not five. Two of your five are the same code, and three you did not list (Cmd+Shift+T, the browser side effect, task-row click) also create sessions. Detail in the current-state map below.

The composer

Do not invent this. NewTaskComposerStore already implements the exact state machine — single-instance-at-a-time, focus trigger, a three-step smart-default project cascade (NewTaskComposerStore.swift:168–195: frontmost terminal cwd → MRU → most-recently-touched), an inline + Add project… chip that runs the folder picker without closing the composer (:162), inline error state, Esc cancel. It commits a .md task instead of a session, so it cannot be reused directly — but its shape is the answer and the new store should be a deliberate mirror of it, file-adjacent and same naming.

Whether one field still filters both is now open, not settled — see decision 3 below. Giving the project its own trailing control (Treatment 2, locked) makes the original "one field filters templates AND projects" idea either redundant-by-design or abandoned; Sean has seen it both ways in the mockups and has not chosen. The strawman keeps filtering both, so Cmd+T, type bru, Return still lands you in a Brukas session — no submenu, no scanning — while the trailing control becomes the discoverable, explicit path to the same place.

No name field, deliberately. An unpinned session's sidebar name is its live terminal title, so anything typed at creation is overwritten within seconds unless it also pins. Naming stays one-way (your call, 2026-08-10). createQuickSession keeps auto-naming "\(template.name) \(count + 1)" at SessionCoordinator.swift:315.

Centered presentation: in-window overlay, not NSPanel

Correction: there is already a centered-panel pattern. Four floating overlays ship today — UpdateOverlay (TerminalView.swift:128), SurfaceSearchOverlay (SurfaceView.swift:165), buildInfoBadgeHostingView (WorkspaceViewContainer.swift:165, constrained at :1507–1508), and the closest analog, CommandPaletteView (CommandPalette.swift:60) — a Spotlight panel with keyboard nav, focus handling, and focus restoration already solved, presented as a SwiftUI overlay in a ZStack+GeometryReader offset 5% from the top (TerminalCommandPalette.swift:22–43). The recommendation is unchanged — an in-window overlay, a TransparentHostingView<SessionComposerOverlay> added as a subview of WorkspaceViewContainer, hosted by that same purpose-built subclass at WorkspaceViewContainer.swift:1701 — but it now follows a shipped pattern instead of inventing one.

An NSPanel would be the textbook answer and it is the wrong one here. A second window brings its own key/main handling, its own responder chain for Esc, floats above other apps when Ghostties is not front, and needs one instance per terminal window. The overlay inherits the window it belongs to for free, and it reads as part of the app rather than as a system dialog — which is what "tied to the entry point" actually means for a keystroke: tied to that window.

The cost, stated more precisely. It means touching WorkspaceViewContainer — home to both the shadowPath fragility and the projectFirst measurement beachball — but not into the unknown: buildInfoBadgeHostingView (:165, constrained at :1507–1508) is the fork's own shipped precedent for a constraint-only floating hosting view, so this follows the pattern that already works here rather than braving a minefield. Three non-negotiables still apply: use Auto Layout constraints the way buildInfoBadgeHostingView does and never touch layout() at :572; pin the width explicitly (.frame(width:)) so SwiftUI never negotiates size with the container — the exact fix that killed the projectFirst loop; add and remove the subview on demand so no hidden hosting view participates in layout while closed.

Fork-vs-build is decided: fork a copy. Calling CommandPaletteView as-is cannot deliver the locked design — every part that must change (CommandPaletteQuery at :222, CommandTable at :287, CommandRow at :337) is private, and the only exposed knobs are isPresented, backgroundColor, options. So the real choice is only copy-or-build, and copy wins: it starts from working arrow/⌃P/⌃N nav with wraparound, selection clamping, auto-select-first-on-type, match highlighting including initials matching, scroll-to-selection, hover, empty state, material card, and scheme derivation — all on a plain VStack, not LazyVStack, which already satisfies the frozen-rows constraint from PR #121. Editing CommandPalette.swift in place is ruled out: git diff upstream/main HEAD -- "macos/Sources/Features/Command Palette/" is 2 lines, all in TerminalCommandPalette.swift — CommandPalette.swift is byte-identical to upstream, and editing it converts a zero-conflict file into a permanent rebase liability. The copy lands at macos/Sources/Features/Ghostties/SessionComposerPalette.swift, renamed and parameterized.

Phasing

Each phase is independently mergeable and each is written for an implementer with no memory of this document. Smallest first — Phase 1 ships real user-visible value with zero new UI surface.

Phase 1 · One template resolver, name-first templates

  • New file macos/Sources/Features/Ghostties/SessionTemplateResolver.swift with one function: static func templates(for project: Project, store: WorkspaceStore) -> [AgentTemplate]. Filter isGlobal || projectId == project.id; partition the project's defaultTemplateId to the front; keep insertion order within each partition; presets (templateDescription != nil) group before built-ins group before user templates.
  • Repoint both callers. Delete RecentsListView.availableTemplates(for:store:) (:152–160, including the invalid sort at :156) and the three computed filters in TemplatePickerView (:32–43). Both call the resolver. Fixes D5 and D6.
  • Name-first template creation. Replace addCustomTemplate() at TemplatePickerView.swift:336–339: the + New template… row becomes an inline text field in place, Return commits via store.addTemplate with the typed name, Esc discards and writes nothing. Never persist an unnamed record. Fixes D4.
  • Dedupe on write in WorkspaceStore.addTemplate — an exact name collision appends " 2", " 3". Backstop for the case where a user types the same name twice.
  • Empty state in the YOUR TEMPLATES section: one secondary line, no emoji, e.g. "Presets above cover most cases." Shown only when the section is empty.
  • Ship gate: three identically-named templates cannot be recreated by any click sequence; a project-scoped template appears in exactly one project's list. Add a unit test on the resolver with a mixed global/scoped fixture.

Phase 2 · SessionComposer, popover only

  • New files SessionComposerStore.swift, flat in macos/Sources/Features/Ghostties/, and SessionComposerPalette.swift — a forked copy of CommandPalette.swift, renamed and parameterized (the fork-vs-build decision above). The store still mirrors NewTaskComposerStore.swift — read it first and match its shape: static let shared, @Published isOpen, focusSearchFieldTrigger, selectedProjectId, searchText, writeError. Copy the cascade at :168–195 and the add-project chip at :162; do not import the task store, it commits a .md.
  • Request type SessionComposerRequest { presentation: .anchored | .centered; projectBinding: .locked(Project) | .prefilled(Project) | .open; }. Nothing else parameterizes it.
  • View anatomy per the mock above: search field with a trailing divided project control (hairline rule, project name, ▾ — Treatment 2, no separate project-chip row), RECENT section (last three (project, template) pairs, persisted to @AppStorage), TEMPLATES section from the Phase 1 resolver, + New template… footer, and + Add project… as the last row in the open project dropdown, mirroring NewTaskComposerStore.swift:162. CommandPaletteView has no section headers — :303 is a flat ForEach — so the RECENT/TEMPLATES grouping must be added; TemplatePickerView.swift:83,110 is the header precedent. Plain VStack, never LazyVStack.
  • Remove or gate the focus-loss auto-dismiss. CommandPalette.swift:264–268 fires .exit on text-field blur, closing the panel — the trailing project dropdown and + Add project…'s NSOpenPanel both take first responder and would kill the composer mid-interaction under the inherited behavior. Ship gate: open the project dropdown, pick a project, composer still open; + Add project… opens the folder picker and the composer survives it.
  • Build prefix-first relevance ranking. filteredOptions (CommandPalette.swift:74–92) is boolean match then colorMatchScore only — nothing guarantees "type three characters, press Return" lands on the right row, and the color scoring means typing "blue" surfaces rows by dot color. Not inherited; must be built. Ship gate: typing a project's or template's distinctive prefix and pressing Return always starts that session.
  • Four smaller inherited constraints to budget for.   • Wire one call site only. ProjectDisclosureRow.swift:452's .popover renders SessionComposerPalette with .locked(project). Invert the Option polarity at :461 — plain click opens the composer, Option-click keeps today's instant create. Fixes D3.
  • Leave TemplatePickerView in the tree — it still owns the preset preview card, the edit sheet, and the duplicate/delete context menu. Phase 2 replaces the list, not the file.

Yours to decide — three forks, each with a strawman

  1. Does the centered composer dim the terminal behind it?
    Strawman: yes — a black scrim at 0.25 across the container. Ghostties has two shadow levels and no modal vocabulary at all; on a busy dark terminal a card with only the overlay shadow (0.20/12/0) loses its edge and reads as terminal content. The scrim is what makes it read as "on top of."
    Alternative: no scrim, shadow only. Quieter and more tool-like, at the cost of edge definition. Reversible either way — it is one modifier.
  2. Cmd+T opens the composer, or stays instant?
    Strawman: Cmd+T opens the composer with everything pre-filled and Return commits, and Cmd+Shift+T — already a hidden alias — becomes the true zero-UI instant create. You gain a visible target on the chord you actually press, and keep an instant path for when you do not want one.
    Alternative: Cmd+T stays instant and the composer gets Cmd+Option+T. Preserves muscle memory exactly, but a panel behind a three-modifier chord is a panel nobody opens.
  3. Does the search field still filter projects, or templates only?
    Strawman: keep filtering both. Giving the project its own dedicated trailing control (Treatment 2, locked) makes the plan's original "one field filters both" idea either redundant-by-design or abandoned — Sean has seen it both ways in the mockups and has not chosen. Keeping both filtered means "type bru, press Return" survives as the fast path, and the trailing control becomes the discoverable, explicit path to the same place.
    Alternative: field filters templates only; project selection is exclusively via the trailing control. Cleaner mental model, but kills the single-fastest path for the common case where you already know the project.

Not a decision, just so it is not re-litigated: the composer has no session-name field. An unpinned session's sidebar name is its live terminal title, so anything typed at creation is overwritten within seconds. Naming stays one-way.
