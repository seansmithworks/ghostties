Design-system reference site + marketing assets

A docs-only reference page for the app's real tokens, plus a checklist for the marketing asset set

Project: Ghostties 2026-08-18 Draft — 2 forks open

The plan

Fix the token drift first, then build one page that documents both systems side by side, and ship it as a local file — not a route on ghostties.org. The reference site's only job is to be true to what's in code today. Building it before the drift is fixed just re-publishes the same lie DESIGN.md already tells.

  • Token drift gets fixed in DESIGN.md itself — three edits, no code changes, done before the reference site is written.
  • One site, two clearly separated systems — Mac app and website each get their own section, because they don't share tokens and pretending otherwise is how the next drift starts.
  • Lives at docs/design-system/index.html, opened locally, never deployed. It's an internal reference, not marketing — it documents private SwiftUI hex values and dynamic-color approximations that have no business on the public site, and web/ auto-deploys to production on merge.
  • Marketing assets are a checklist, not a build — app icon plus five screenshots, every capture step done by Sean at the desk (screen-capture permission is gated per-terminal-session and can't be scripted around).

Token drift — fix before documenting

Three edits to DESIGN.md, all documentation-only — nothing in WorkspaceLayout.swift changes. The audit (docs/audits/sidebar-contrast-audit.md) already did the comparison work; this just applies it.

Problem Fix
textPrimary / textSecondary are fixed hex values in DESIGN.md §2, but the code uses Color.primary / .tertiaryLabelColor — system dynamic colors with no static RGBA. They're not the same mechanism, and the fixed hex is what's currently wrong (the contrast audit's whole finding). Relabel the row "System dynamic — approximate, not canonical." Keep the hex as a rendering reference (useful for mockups) but stop calling it the implementation. The real token is the API call, not a hex code.
DESIGN.md's "Activity indicator states" table lists only Waiting: waitingTerracotta. The palette that actually ships — blue/gold/orange status dots plus system green — replaced terracotta in status dots back in June and was never written back. Replace the table with the four real states, values pulled straight from WorkspaceLayout.swift: green=working (system), blue=your-turn #5B8DEF, gold=needs-decision #FFC400, orange=long-running #F97316. Terracotta stays documented separately as "brand accent — chrome elements, not status," matching where it still ships.
border, destructive, success are documented in DESIGN.md §2 but don't exist anywhere in WorkspaceLayout.swift or the fork's Swift files. Delete the three rows. Aspirational tokens with zero call sites aren't a design system, they're a wish list — and the reference site should never show a swatch nobody can find on screen.

Not in scope here: the contrast failures themselves (status dots at 1.3–2.7:1 in light mode). Sean has deliberately deferred that fix because it touches his chosen palette — the reference site documents the dots as they ship today, contrast failure and all, with a callout linking the audit. Documenting a wrong value is drift; documenting a known-imperfect value with a link to the fix-in-progress is honest.

Two systems, not one

The app and the website are separate products with separate DESIGN.md files, separate palettes (warm chrome/canvas vs. near-black #1a1a2e), and separate type stacks (SF Pro/SF Mono vs. system sans/mono). A reference page that merges them into one token list would either force a fake reconciliation or silently pick one and call it canonical. Neither is true. The page gets two top-level sections — App and Site — each sourced from its own DESIGN.md, with no shared token table between them. If a value is ever meant to match across both (it isn't today, beyond the terracotta hex itself), that's a design decision to make explicitly, not an artifact of building one page.

Where it lives

Path docs/design-system/index.html (+ one CSS file alongside it, not shared with web/style.css)
Served how open docs/design-system/index.html, or python3 -m http.server from that folder — never deployed, never linked from ghostties.org nav
Why not web/ Merging to main is a production deploy of ghostties.org. A page full of internal SwiftUI hex approximations and "known contrast failure" callouts is not something to accidentally ship to visitors on the next unrelated web PR.
Updated how By hand, same discipline as any doc — when WorkspaceLayout.swift or web/style.css changes a value that's on the page, update the page in the same PR. No generator, no build step; it's one static file.

At-the-desk capture checklist

Every step below is Sean, at the machine, by hand. Screen-capture permission is granted to the terminal, not the app being photographed, and a visibly-on toggle can still deny silently — the fix requires a relaunch that would kill this session. No agent can safely drive this.

  1. Set up the scene by hand — the sessions, projects, and mode (light/dark, pinned/overlay) each shot calls for.
  2. Run screencapture -D 2 from a real Terminal window, not inside the automated session — the interactive delay lets you click into the target window first.
  3. Save straight to images/marketing/ with a name matching the row in the table above (e.g. hero-dark.png, sidebar-light.png).
  4. For the app icon: export at 1024×1024 from the existing icon source in images/; no new capture needed.
  5. Hand the files to whichever agent is doing the reference-site build or the web PR — that part can be delegated once the PNGs exist.

Yours to decide — two forks, both with a strawman

  1. Does the reference site ever go public?
    Strawman: no, stays local-only indefinitely. It documents private implementation detail — dynamic-color approximations, a known contrast failure, internal SwiftUI token names — that reads as unfinished or overly technical to an outside visitor. A public design-system page is a different, smaller document (palette + type only, no code-level detail) and a separate decision later if there's ever a reason to court that audience.
    Alternative: publish a curated public subset on ghostties.org as a brand/press page. More work, and nothing in the current site plan calls for it — defer until there's a concrete reason (press kit request, etc.).
  2. Do the ghost sequences animate on the page?
    Strawman: static pixel-grid renders only, v1. Motion capture is more desk time for Sean and the mascot's identity is already fully legible frozen — 24 distinct pixel-art characters. Animation adds production cost without adding information the page needs to convey.
    Alternative: screen-record the idle/walk animation per character and embed short loops. Nicer, but it's five more capture sessions' worth of work for a reference page whose job is "what are the 24 characters," not "how do they move." Revisit if the site ever goes toward Fork 1's public-page alternative.

Not a decision, just so it isn't re-litigated: the reference site is not a build target for the app or the site — it never gets imported, linked, or wired into either codebase. It's a document that happens to be HTML because tables and swatches read better that way than in Markdown.
