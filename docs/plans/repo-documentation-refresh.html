The headline

Two things outrank everything else, and they must happen in this order.

1. Your repo currently makes a false public claim of upstream involvement — CODEOWNERS assigns 39 @ghostty-org/* teams as owners of your code, and .github/VOUCHED.td publishes 233 named individuals as vouched contributors to your project. That is the "implying affiliation" risk you named, and it is structural repo data, not README wording.

2. Issues and Discussions are both disabled. The 37 people who starred this have no way to report a bug. But do not enable Issues first — an inherited workflow is armed to auto-close the first stranger's bug report with a message linking to upstream's contributing guide.

You asked for a documentation review. The documentation is the smaller half of the problem. The larger half is that this fork inherited upstream's entire community-governance apparatus — workflows, owner lists, contributor rosters, policy docs — and none of it was ever removed. A visitor who clicks "Contributing" on Ghostties reads Mitchell Hashimoto's personal-project rules. A visitor who reads CODEOWNERS concludes the Ghostty organization maintains your sidebar.

The good news: your original documentation is genuinely good. CHANGELOG.md is the best-written file in the repo — plain product prose explaining what each change means for a user, not a commit log. Your issue templates are already Ghostties-specific and well-structured. The website's licenses.html already credits Ghostty and CEF properly. The problem is almost entirely inherited material that was never pruned, plus a README that is too thin to convert the traction you're now getting.

Ghostties vs. Ghostty: the calibration

I had a research agent read the live READMEs of eleven forks of famous projects — VSCodium, OpenTofu, Ladybird, Valkey, Forgejo, LibreWolf, Zen Browser, ungoogled-chromium, Vaultwarden, Void, Positron. The pattern contradicts folk wisdom in a useful way:

Mature forks state the relationship in the first two sentences and then never mention it again. None have an "Attribution" section near the top. None lead with an apology or a gratitude paragraph. The relationship is stated once, as information the reader needs to make a decision — not as deference.

Three patterns worth stealing:

VSCodium leads with the negation — line 21, bolded, before anything else: "This is not a fork. This is a repository of scripts to automatically build Microsoft's vscode repository into freely-licensed binaries…" It tells you what it isn't first, because the misconception is what stands between the reader and understanding.

Vaultwarden solves the operational half with an > [!IMPORTANT] callout high in the README: "When using this server, please report any bugs or suggestions directly to us… DO NOT use the official Bitwarden support channels." That callout does more work than their legal disclaimer — it protects Bitwarden's issue tracker from Vaultwarden's users. For you, that's the real concern: you don't want Ghostties sidebar bugs landing on ghostty-org.

Zen Browser states the upstream version per channel: "Release — Is currently built using Firefox version 153.0.1!" A "Built on Ghostty v1.2.x" line is the single most useful piece of fork-identity information for a technical user. It tells them which upstream bugs and features they have, and it silently proves you're tracking upstream rather than rotting on a stale base.

On the non-affiliation line

Only 1 of 7 forks surveyed uses an explicit "not affiliated" line. It is not standard practice. It becomes standard in two cases: the upstream is a company with a support burden, or your name is confusingly derived from theirs.

You are the second case. "Ghostties" is one character from "Ghostty" — same phonetic root, same product category, same distribution channel. Note that every other mature fork chose a non-derived name specifically to avoid this: Gitea→Forgejo, Redis→Valkey, Terraform→OpenTofu, Firefox→LibreWolf. The one derived-ish name in the set (Bitwarden→Vaultwarden) is also the one carrying the explicit disclaimer.

Also worth being precise about: MIT grants you nothing on the name. MIT is a copyright license and is silent on trademarks. Your right to use a Ghostty-derived product name is governed by trademark law, not by the license you inherited.

Unverified: whether "Ghostty" is a registered or common-law mark. Upstream's repo has no TRADEMARK.md or published brand policy, and I did not check USPTO records. Proposed language sidesteps the question by asserting respect without a factual claim about registration:

## License

Ghostties is [MIT licensed](LICENSE), the same license as upstream Ghostty.
Ghostties is an independent project and is not affiliated with, endorsed by,
or sponsored by the Ghostty project or Mitchell Hashimoto. "Ghostty" is a mark
of its respective owner.

Third-party components are listed in [THIRD-PARTY-NOTICES.md](THIRD-PARTY-NOTICES.md).

Placement at the bottom, in the License section — top placement makes it read like a legal threat hangs over the project.

SECURITY.md — new, and this is your highest-priority supporting file. Upstream doesn't have one, so you can't inherit it. Issue forms (YAML), replacing the markdown templates. Your current templates are good, but markdown templates pre-fill a textarea and users routinely delete it and type a paragraph. YAML forms render real inputs with required: true that GitHub enforces client-side — the user physically cannot submit without a version number. For a solo maintainer the entire value of a template is eliminating the "what version are you on?" round-trip. Forms do that; markdown doesn't.

The field worth calling out, which no other fork seems to do:

- type: dropdown
  id: upstream
  attributes:
    label: Does this also happen in upstream Ghostty?
    description: If it does, it's likely an upstream bug and belongs on their tracker.
    options:
      - "No — Ghostties only"
      - "Yes — happens in Ghostty too"
      - "Haven't tried"
      - "N/A — this is a Ghostties-only feature"
  validations:
    required: true

That single field sorts "your bug" from "upstream's bug" before you spend an hour on it. It's the highest-value field a fork can have.

Also: set blank_issues_enabled: false (the "open a blank issue" escape hatch defeats the forms), and add a Discussions contact link alongside the upstream one you already have — that upstream redirect was a genuinely smart call and it stays.

Labels — six, two axes. Type: bug, enhancement, question. State: needs-triage, confirmed, upstream. That last one is the fork-specific bucket for "real bug, not mine, here's the upstream link" and it'll be your most-used label. Auto-apply needs-triage from the form so your triage view is just is:open label:needs-triage. Delete good first issue and help wanted — you're not taking code PRs, and a stale good first issue is a worse signal than no label.
