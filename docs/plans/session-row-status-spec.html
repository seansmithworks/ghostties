Recommendation: the row keeps its single ghost glyph as the primary read, and gains one optional second line underneath the name. That line is absent when there's nothing to say (the common case), a progress fragment when a todo list exists, and an accent-colored action when the session is genuinely blocked on the user. A chevron only appears when there's a list to disclose — never as a dead affordance.

How the action is displayed, and what clicking it does

The action line replaces the progress line (a row shows one or the other, never both) and is the only place terracotta appears outside the glyph — DESIGN.md already reserves that color for the waiting/blocked state, so the action pill spends the same accent budget rather than opening a new one. The text itself is the actual blocking question, not a generic "needs attention" label — sourced from the same live-state read that produces the glyph color, not invented copy.

Clicking it does exactly what clicking the row already does today: focuses that session's terminal and scrolls it to the bottom. No modal, no inline approve/deny — Ghostties doesn't have a side-channel to the agent that a click could satisfy, so the affordance is "take me there," not "resolve this here."

Degrading into the Projects view

Projects don't get the accordion — a project row is a group, and disclosing every child's todo list two levels deep would defeat the density agent-craft.md asks for. It gets the same vocabulary, compressed: the project's ghost glyph tints to the highest-priority child state (error > needsAttention > waiting > longRunning > processing > idle — this ordering already exists for the menu bar per agent-experience.md, reused rather than invented), and a project with at least one blocked child shows a one-line count instead of a name: 2 need you in terracotta, replacing the normal subtitle. No progress fractions at the project level — that detail is what expanding into Sessions is for.

What has to exist first

This entire design is downstream of one gap: AgentSession carries no pid and no sessionId (Models/AgentSession.swift:10-51), so a row has no way to locate its own todo file or its own live-status file. Until that join exists, every element above the base glyph is unbuildable — this is a dependency, not a phase to schedule.

The join path already exists as the launcher-UUID script (~/.ghostties/cache/launchers/<sessionUUID>.sh), but it's only written when template.launchBanner is set (SessionCoordinator.swift:224), which is why only 8 of 13 live sessions have it today. Closing that gate to write unconditionally is the smallest fix that gets coverage to 13/13.

The state-source fork

Today's needsAttention/waiting are inferred from terminal output heuristics, and a direct measurement caught that inference lying at scale: 7 sessions genuinely idle, 4 genuinely busy, zero genuinely waiting — while the sidebar painted nearly all of them as attention states. .idle depends on OSC 133, which Claude's TUI never emits, so .waiting isn't a real wait state today, it's the branch inference falls into when it can't tell what's happening.

Building the richer row on top of that inference would just make the lie more visible — a progress fraction and a named action look authoritative, and an authoritative-looking wrong answer is worse than today's vague glyph, because it teaches Sean to stop checking the terminal himself. Recommendation: read real state from ~/.claude/sessions/<pid>.json instead of inferring it. That file already carries status, and pairing it with the todo file gives both the state and the detail for free, from data the agent itself wrote — no heuristic in between. The cost is real: it requires the pid/sessionId join above, plus a live file-watcher on two directories instead of the existing output-heuristic timer. That's the one thing this recommendation gives up — inference is already running and cheap; reading is a build. Sean is trading a small amount of build time now for a badge he can trust indefinitely, which is the right trade for a status surface whose entire job is to be believed at a glance.

Decisions for Sean

1. Infer status vs. read it from ~/.claude/sessions/<pid>.json Recommend: read. Inference is measurably wrong at the rate this richer row would expose; a trustworthy badge is worth the extra build (file-watcher + join) over the cheaper heuristic.
2. Close the template.launchBanner gate so every session gets a launcher script Recommend: yes, write it unconditionally. It's the one change that takes join coverage from 8/13 to 13/13 and nothing in this spec works below full coverage.
3. Show a progress/second line for every non-default state, or only when a todo list exists Recommend: only when a todo list exists. 95% of rows never call TodoWrite; a "processing" label with nothing under it just adds noise back to a row that today is deliberately quiet.
4. Project-row aggregate: a "N need you" count vs. reusing the child's glyph tint alone Recommend: add the count. The tint alone answers "is something wrong in here," not "how many things," and Sean's actual question in the ask was sizing the action, not just spotting it.
