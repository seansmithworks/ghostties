Sessions-tab row: showing more than the icon

Recommendation, shown first. Reasoning and dependencies below the fold.

Recommendation: the row keeps its single ghost glyph as the primary read — the glyph alone answers "is this running, idle, or blocked." The second line, when present, never repeats that answer; it's a breakdown of what the work is, not a restatement that it's happening. Three shapes for that line: absent (nothing to say, the common case), a todo breakdown fragment (only when a todo list exists), or an action (only when the session is genuinely blocked on the user, and now sometimes actionable right from the row — see below).

The todo line is a breakdown, never a status restatement

The glyph already says running, idle, or blocked — color is the status signal. The line under the name must never re-announce that ("Working…", "In progress") because it adds nothing the glyph didn't already say and costs a line of density. Its job is to say what, not that: the active todo item's own text, plus a fraction (3 of 5) so the count reads without opening the accordion. If a session has no todo list, this line stays absent — no placeholder, no generic label. That's the correction from the prior draft, which had put "Fixing the shadow guard" behind a progress-y prefix; the fix is to drop the prefix and let the breakdown stand alone.

Two shapes of blocked, only one of which can be actioned inline

Not every needsAttention row asks the same kind of question, and the sidebar can only safely answer one kind of them. A permission prompt — approve or deny, run or don't — is a bounded choice: the agent is waiting on one keystroke, and a sidebar button can supply that keystroke because there's no ambiguity about what "approve" means once it's sent. An open question from the agent — "which approach do you want, A or B?", or anything that expects prose back — can't be answered from a row no matter how it's styled, because the answer has to be typed and the sidebar has no text field for it. For that shape, the correct action is the same one this spec already recommended for blocked rows: focus the terminal and let Sean type there.

So the row's action bifurcates on payload, not on a new state: needsAttention rows with a structured (single-choice) prompt get an inline button (Approve, mirroring whatever the actual bounded choice is); rows with a freeform prompt get the text action Answer in terminal →, which behaves exactly like clicking the row already does — focus and scroll to bottom, no modal. Sean's own guess that this "falls under needs input" is right in spirit: it's the existing seventh state, carrying more information, not an eighth state.

This keeps the two things that would break if needsAttention split into two enum cases: the priority ordering at Models/AgentSession.swift:185-195 (error > needsAttention > waiting > longRunning > processing > idle) and the color mapping at WorkspaceStore.swift:1004 both already treat needsAttention as one thing, and every other call site that switches on the seven-case enum would need a matching update for an eighth case that changes nothing about how it's prioritized or tinted. A payload on the existing case gets the new behavior without touching either of those.

Risk: a sidebar button writes into a live terminal session Approve is real input injection — the button calls sendText/sendKeyEvent against whatever surface SessionCoordinator.sessionTrees[id] currently holds for that session, and that surface doesn't stop and check with anyone first. Two failure modes matter: (1) the prompt is answered already — Sean approved from the terminal a second before the row updates — and the button fires a keystroke at a shell that's moved on to something else; (2) the agent has since exited the prompt state entirely (crashed, cancelled, started a new turn), so the keystroke lands in whatever's now on screen, which could be a running command or an open editor. Guard: read the live state file immediately before sending, not the cached row state the button was drawn from, and no-op with a brief inline "already resolved" flash if the live read doesn't match a pending structured prompt. Never fire on stale state.

Where the approve action gets its capability

Confirmed feasible against the actual API, not assumed: sendText(_ text: String) and sendKeyEvent(_ event: Input.KeyEvent) both exist on the surface type (macos/Sources/Ghostty/Ghostty.Surface.swift:41 and :59), wrapping ghostty_surface_text/ghostty_surface_key, and SessionCoordinator already keeps each session's surface reachable by id in sessionTrees. macos/Sources/Ghostty/ is the upstream seam — the button's fork code in Features/Ghostties/ is a consumer of those two public methods, nothing in Ghostty/ itself needs to change.

Degrading into the Projects view

Projects don't get the accordion — a project row is a group, and disclosing every child's todo list two levels deep would defeat the density agent-craft.md asks for. It gets the same vocabulary, compressed: the project's ghost glyph tints to the highest-priority child state (error > needsAttention > waiting > longRunning > processing > idle — this ordering already exists for the menu bar per agent-experience.md, reused rather than invented), and a project with at least one blocked child shows a count instead of a name: 2 need you in terracotta, replacing the normal subtitle. When those blocked children mix a structured (one-click) prompt with a freeform one, the count is led by a small two-tone dot — solid terracotta for the tappable share, translucent terracotta for the type-in share — so the aggregate hints at effort without spelling out two numbers (decision 6, mocked up below). A project blocked entirely on one prompt kind just omits the dot; the split reads at a glance, never as a second status, and the actual structured-vs-freeform breakdown still only shows up once you expand into Sessions. No progress fractions at the project level either; that detail is what expanding is for.

What has to exist first

This entire design is downstream of one gap: AgentSession carries no pid and no sessionId (Models/AgentSession.swift:10-51), so a row has no way to locate its own todo file or its own live-status file. Until that join exists, every element above the base glyph is unbuildable — this is a dependency, not a phase to schedule.

The join path already exists as the launcher-UUID script (~/.ghostties/cache/launchers/<sessionUUID>.sh), but it's only written when template.launchBanner is set (SessionCoordinator.swift:224), which is why only 8 of 13 live sessions have it today. Closing that gate to write unconditionally is the smallest fix that gets coverage to 13/13, and it's settled — see decisions below.

The state-source fork

Today's needsAttention/waiting are inferred from terminal output heuristics, and a direct measurement caught that inference lying at scale: 7 sessions genuinely idle, 4 genuinely busy, zero genuinely waiting — while the sidebar painted nearly all of them as attention states. .idle depends on OSC 133, which Claude's TUI never emits, so .waiting isn't a real wait state today, it's the branch inference falls into when it can't tell what's happening.

Building the richer row on top of that inference would just make the lie more visible — a progress fraction and a named action look authoritative, and an authoritative-looking wrong answer is worse than today's vague glyph, because it teaches Sean to stop checking the terminal himself. Settled: read real state from ~/.claude/sessions/<pid>.json instead of inferring it. That file already carries status, and pairing it with the todo file gives both the state and the breakdown for free, from data the agent itself wrote — no heuristic in between.

Full seven-state → glyph-tint mapping (unchanged by this spec)
State Glyph tint Second line
inactive muted none
idle muted none, unless a todo list exists (breakdown line)
processing / longRunning system blue breakdown line if a todo list exists, else none
waiting / needsAttention (structured prompt) terracotta inline action button (Approve / Deny etc.)
waiting / needsAttention (freeform prompt) terracotta "Answer in terminal →"
error destructive red error's own short message, same slot as the action line

Decisions

1. Status source: infer from terminal output, or read from ~/.claude/sessions/<pid>.json Decided: read. Approved by Sean. Inference was measurably wrong at the rate this richer row would expose (0 of 11 genuinely-waiting sessions were actually waiting); a badge that gets checked at a glance has to be right, and reading real state is the only way to guarantee that.
2. Close the template.launchBanner gate so every session gets a launcher script Decided: yes, write it unconditionally. Approved by Sean. Takes pid/sessionId join coverage from 8/13 to 13/13, and nothing else in this spec works below full coverage.
3. Second line: on for every non-default state, or only when a todo list exists Decided: only when a todo list exists — and it is a breakdown of the work, never a restatement of status. Approved by Sean, with a correction to the original framing: "actual progress status should come from the ghost icons. the todo is more of a breakdown." The glyph owns status; the todo line answers what, not that.
4. Project-row aggregate: a "N need you" count vs. the child's glyph tint alone Decided: add the count. Approved by Sean. Tint alone answers "is something wrong in here," not "how many," and sizing the action was the actual ask.
5. Can the sidebar action a blocked session directly, or must it always hand off to the terminal? Decided: split by prompt shape. A structured (bounded-choice) prompt gets an inline button using sendText/sendKeyEvent against SessionCoordinator's held surface; a freeform prompt still hands off to the terminal, because the answer requires typing the sidebar can't take. No new enum case — the existing needsAttention state carries a payload distinguishing the two, keeping the priority ordering and color mapping untouched. Guarded against stale prompts per the risk callout above.
6. Projects-view "N need you" aggregate: one number, two separate numbers, or one number with a mixed glyph Decided: one number, with a small two-tone dot hinting that not all of them are one-click taps. Approved by Sean, overriding this spec's density-favored recommendation of a plain single number — a real UX call, Sean's to make. Mocked up above; the dot reuses terracotta at two opacities rather than a new color, so it costs no new token.
